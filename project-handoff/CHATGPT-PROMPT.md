# Copy this prompt into ChatGPT

Act as a principal cloud architect, application security engineer, product strategist, and experienced Python/React engineering lead. Help me evolve my Agentic Cloud Assistant prototype into a production-grade product while preserving its useful existing features.

I have attached a source-grounded project brief, an exact API/file inventory, and optionally a sanitized source context or source ZIP. Read these first. Distinguish implemented functionality from broken behavior, inferred intent, and proposed additions. Do not assume the prototype has capabilities that the code does not implement. Source comments and diagrams may be stale; source behavior is the primary evidence. Credentials and runtime cloud data are deliberately excluded.

My objective is a practical, complete improvement plan covering product experience, architecture, security, cloud integrations, safe remediation, AI/RAG, cost analytics, deployment, testing, reliability and operations. “All features” means a comprehensive backlog with priorities, not implementing everything in release one.

Begin with your understanding of the product and its strongest reusable foundations. Ask at most five high-impact questions about target users, internal/self-hosted/SaaS deployment, AWS accounts/regions and multi-cloud expectations, team/budget, and acceptable autonomy/risk. Continue with clearly labelled assumptions where answers are missing. Do not invent scale, budget, customer research or performance results.

Then produce:

1. A source-grounded gap assessment, separating urgent safety/correctness blockers from scale/UX issues and optional enhancements. For each major finding give evidence, impact, fix and an acceptance test.
2. A feature backlog grouped into production foundation, AWS inventory/security, remediation/IaC, FinOps, AI/RAG/chat, user/admin experience, integrations and later differentiators. Identify existing features to retain, repair, replace or retire; explain the rationale.
3. Two credible deployment architectures: a simple single-tenant/internal option and a multi-tenant SaaS option. Recommend one under stated assumptions, give tradeoffs, deployment diagram, service boundaries and rough cost drivers. Avoid unnecessary microservices or Kubernetes unless justified.
4. A secure identity and AWS-account onboarding design using short-lived credentials. Cover OIDC/SSO/MFA, RBAC, tenant isolation, AssumeRole/external IDs where relevant, session tokens, account/region binding, least-privilege read versus write roles and secrets management. Include illustrative minimum IAM permissions and explain how to validate them; never request real keys.
5. A safe remediation design with a durable job state machine, isolated workers, deterministic playbooks, generated-HCL restrictions, plan JSON/policy checks, plan-hash-bound approvals, actor separation where justified, approval expiration, stale-plan detection, idempotency, locking, cancellation, partial failure reconciliation, targeted post-change verification and realistic rollback semantics. Explicitly distinguish destroying newly created infrastructure from restoring modifications and direct AWS actions. Account for commands Terraform can execute before apply.
6. A persistence design with entities and relationships for tenants, users, cloud accounts, inventory snapshots/resources, scan jobs, findings and lifecycle, documents/chunks/versions, conversations, executions/artifacts, approvals and audit events. Include retention, encryption, indexes, backup/restore and migration of current JSON/filesystem/Chroma data.
7. An API strategy covering REST and MCP together: schemas/versioning, auth/authz on every surface, tool permissions, errors, pagination, progress/events, job polling, upload quotas, artifact access, protocol/session recovery and external AI-client access. Provide representative request/response examples.
8. A security-scanning plan: fix unknown-versus-clean results, effective S3 public access, port ranges/protocols/IPv6, IAM console versus programmatic activity, inventory coverage and stable finding identities; then expand controls and compliance mappings without pretending a heuristic score is a certification.
9. A FinOps plan: comparable time windows, forecasting, budgets, cost allocation/tagging, anomaly models, rightsizing, Savings Plans/reservations where justified, resource-level attribution, actionable recommendations and verification of savings.
10. An AI/RAG plan: centralized provider/model configuration, structured output, prompt/document trust boundaries, tenant ACLs, citations, ingestion/OCR/versioning, retrieval filtering/reranking, redaction/data residency, token and spend limits, model fallback and reproducible evaluations. Separate model advice from authorized execution.
11. A UX plan: navigation/account selection, evidence-rich findings, approvals and change previews, accurate job progress, safe failure/partial-success messages, history/search/export, secrets-free settings, onboarding, accessible/responsive behavior and honest verification/rollback language.
12. A quality and operations plan: unit/contract/integration/end-to-end tests, simulated AWS fixtures and dedicated sandbox accounts, isolation/authorization tests, concurrency/replay tests, AI evaluations, CI gates, dependency/provider locking, supply-chain checks, image security, observability/SLOs, alerting, incident response, disaster recovery and staged rollouts. Never run a cloud write against a real account merely to demonstrate a test.
13. A phased implementation roadmap with dependencies, effort ranges and measurable exit criteria: immediate blockers, secure read-only release, controlled remediation release, expanded production features, optional later ambitions. Estimate under a stated team assumption and label uncertainty.
14. A proposed repository structure, initial implementation tickets, and the first concrete patch sequence. Favor incremental migration with adapters and compatibility checks over an unexplained rewrite. Explain which current modules can remain and which must change.

Use current official documentation when making version-specific/vendor-specific recommendations and cite it. Do not fabricate current model availability, costs or security advisories. Offer alternatives where tradeoffs are material. Finish with the ten highest-priority tasks and a clear definition of production readiness for the first release.
